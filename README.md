# LoaAgent — 로스트아크 멀티 에이전트 AI 어시스턴트

LangGraph 기반 멀티 에이전트로 **경매장 시세 조회 · 캐릭터 정보 조회 · 레이드 공략 RAG 검색**을 하나의 대화창에서 처리하는 개인 프로젝트입니다.
라우터가 질문 의도를 분류해 4개의 전문 에이전트 중 하나로 보내고, 각 에이전트는 Tool Calling으로 Stove 공식 개발자 API나 벡터 DB를 조회해 답변합니다.

- 📄 설계 문서: [Loa Agent Documentation](https://checkered-harmony-550.notion.site/Loa-Agent-Documentation-41589a1f6399802aa32edcfb2cde3efb?source=copy_link)
- 🎬 데모 영상: [링크](https://drive.google.com/file/d/1omvh1UlLLzKgC0GTsXpyI37yDlNoio6c/view)

## 주요 기능

| 에이전트 | 하는 일 | 사용 Tool |
| --- | --- | --- |
| Router | 질문 의도를 4개 경로 중 하나로 분류 (Structured Output). 분류 실패 시 1회 재시도 후 General Agent로 폴백 | – |
| Market Agent | 경매장 아이템의 전일 평균가·최근 거래가 조회 | `get_market_options` → `search_market_items` |
| Character Agent | 캐릭터 기본 프로필(서버, 직업, 레벨, 전투력, 길드) 조회 | `get_character_profile` |
| Guide Agent | 레이드 공략 문서 RAG 검색, 정보가 부족하면 재검색 | `search_game_guide` |
| General Agent | 인사·잡담 등 일반 대화 | – |

## 아키텍처

```
브라우저 ──▶ Spring Boot (로그인·세션, MySQL) ──▶ FastAPI /chat ──▶ LangGraph
                                                              ├─ Router
                                                              ├─ Market / Character Agent ──▶ Stove API
                                                              ├─ Guide Agent ──▶ Chroma (BGE-M3)
                                                              └─ General Agent
                                                     (모든 에이전트의 LLM: Gemini)
```

Spring Boot → FastAPI 호출에는 연결 3초, 응답 60초 제한 시간을 둡니다(`application.properties`의 `fastapi.*`, 환경 변수로 변경 가능). 시간 초과(504), 연결 실패(503), FastAPI 오류 응답(502)마다 채팅 화면에 다른 안내 문구를 보여 줍니다.

## 기술 스택

- **AI 서버**: Python, FastAPI, LangGraph, LangChain, Gemini (`gemini-3.5-flash-lite`, `.env`의 `LLM_PROVIDER`·`LLM_MODEL`로 변경 가능)
- **RAG**: Chroma, BGE-M3 (Ollama 로컬 실행), MarkdownHeaderTextSplitter
- **백엔드**: Java 21, Spring Boot, Spring Security, Spring Data JPA, Spring Session JDBC, Thymeleaf
- **DB**: MySQL
- **외부 API**: Stove 로스트아크 공식 개발자 API

## 실행 방법

### 사전 준비
- Python 3.10 이상, JDK 21, MySQL, [Ollama](https://ollama.com)
- API 키: Gemini API Key, Stove 로스트아크 개발자 API Key

### 1. AI 서버 (ai-agent)

```bash
cd ai-agent
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

ollama pull bge-m3                # 임베딩 모델
copy .env.example .env            # .env를 열어 API 키 입력 (macOS/Linux: cp)

python utils/DBupdate.py          # 공략 문서를 Chroma에 적재
uvicorn main:fastapi_app --port 8000
```

**LLM 모델 바꾸기**: 모델은 코드가 아니라 `.env`의 `LLM_PROVIDER`(LangChain 공급자 이름, 서비스에서는 `google_genai`)와 `LLM_MODEL`(서비스에서는 `gemini-3.5-flash-lite`)로 정합니다. 코드에는 기본 모델을 두지 않아, 두 값이 없으면 서버가 시작 단계에서 오류를 내고 멈춥니다(설정이 빠졌는데 다른 모델로 조용히 실행되는 것을 막기 위해). LangChain `init_chat_model`로 만들기 때문에 같은 코드로 다른 공급자도 지정할 수 있지만, `google_genai` 외의 공급자는 해당 패키지(예: `langchain-anthropic`)와 API 키가 필요하고 아직 실행해 보지 않았습니다. 패키지가 없으면 서버 시작 시 `ImportError`가 납니다.

**대화 기록 저장 위치**: `.env`의 `CHECKPOINT_DB_PATH`(예: `data/chat_history.sqlite`, ai-agent 폴더 기준)에 SQLite 파일로 저장합니다. 값이 없으면 서버가 시작 단계에서 멈춥니다. 파일은 처음 실행할 때 자동으로 만들어지고 git에는 올라가지 않습니다.

### 2. 백엔드 (backend/loaagent)

1. MySQL에 `loaagent_db` 데이터베이스 생성 (테이블은 실행 시 자동 생성)
2. `src/main/resources/application-secret.properties.example`을 `application-secret.properties`로 복사해 비밀번호 입력
3. HTTPS 설정
   - HTTPS로 실행: `keytool -genkeypair -alias springboot -keyalg RSA -storetype PKCS12 -keystore src/main/resources/keystore.p12 -validity 365`로 인증서 생성
   - HTTP로 실행: 환경 변수 `SSL_ENABLED=false` 설정
4. 실행

```bash
cd backend/loaagent
.\gradlew bootRun                 # macOS/Linux: ./gradlew bootRun
```

5. 브라우저에서 `https://localhost:8080` (HTTP 실행 시 `http://`) 접속 → 회원가입 → 로그인 → 채팅 화면

### 어려운 멀티턴 테스트

```bash
cd ai-agent
python router_eval.py hard
```

위 테스트는 후속 질문 자체에 단서가 있는 경우가 많아, 단서가 없는 질문으로 다시 측정했습니다. 17건입니다.
- **같은 질문**(12건): "그거 자세히 알려줘", "그거 괜찮은 거야?", "다른 건?", "그거 다시 말해줘"를 각각 서로 다른 앞 대화(공략·시세·캐릭터·잡담)와 짝지어, 앞 대화에 따라 정답 경로가 달라지는지 확인
- **두 턴 전**(5건): 바로 앞이 아니라 두 턴 전 주제로 돌아가는 질문(예: 캐릭터 → 공략 → "아까 그 캐릭터 길드는?")

| 유형 | 건수 | 앞 대화와 함께 | 후속 질문만 |
| --- | --- | --- | --- |
| 같은 질문 | 12 | 11 | 2 |
| 두 턴 전 | 5 | 4 | 4 |
| **전체** | **17** | **15** | **6** |

(2026-11-19, 2회 측정, 두 번 모두 같은 결과)
- **같은 질문**: 후속 질문만 넣으면 모두 `general_agent`로 갔지만(정답이 general인 2건만 맞음), 앞 대화와 함께 넣으면 12건 중 11건이 앞 대화에 맞는 에이전트로 갔습니다. 라우터가 앞 대화를 보고 같은 문장을 다르게 분류함을 확인했습니다.
- **틀린 2건**
  - 캐릭터 전투력 → "그거 괜찮은 거야?": `general_agent`로 감. 라우터 기준상 `character_agent`는 "프로필 조회"라, "괜찮은지"라는 평가 질문은 기준에 딱 맞지 않습니다. 기대 경로 자체가 애매한 사례입니다.
  - 공략 → 시세 → "아까 그거 다시 설명해줘": `general_agent`로 감. "아까 그거"가 공략인지 시세인지 사람이 봐도 애매한데, 라우터는 둘 중 하나를 고르지 않고 일반 대화로 보냈습니다.
- **두 턴 전 테스트의 한계**: 맞은 4건은 질문에 "캐릭터", "재료", "가격" 같은 단서가 있어 앞 대화 없이도 맞았습니다. 단서 없이 두 턴 전으로 돌아가는 유일한 질문은 틀렸으므로, "두 턴 전 맥락을 찾아간다"는 것은 이 테스트로 확인하지 못했습니다.

## LLM 오류 처리

Gemini 오류는 LangChain 공통 예외(`langchain_core.exceptions`)로 구분해 다른 안내 문구를 보여 줍니다. 라우터는 LLM 호출 자체가 실패하면(429, 인증 오류, 서버 장애) 재시도·폴백 없이 바로 중단합니다. SDK가 이미 재시도했고, 폴백 대상인 General Agent도 같은 LLM을 쓰기 때문입니다.

| 오류 | 예외 | 안내 문구 |
| --- | --- | --- |
| 사용량 제한(429) | `ModelRateLimitError` | 요청이 많아 잠시 이용이 제한됐습니다. 1~2분 후 다시 시도해주세요. |
| 인증·권한(401/403) | `ModelAuthenticationError`, `ModelPermissionDeniedError` | AI 서비스 설정에 문제가 있습니다. 관리자에게 문의해주세요. |
| 서버 장애(5xx) 등 | `ModelAPIError`, `ModelTimeoutError`, `ModelConnectionError` | AI 서비스가 일시적으로 불안정합니다. 잠시 후 다시 시도해주세요. |
| 그 외 | – | AI 에이전트 처리 중 오류가 발생했습니다. |

컨텍스트 초과는 모든 노드에서 `trim_messages`(12,000토큰)로 입력을 자르므로 별도로 구분하지 않습니다.

```bash
cd ai-agent
python -m unittest test_llm_error_messages -v
```

## 대화 기록 영구 저장

대화 맥락은 LangGraph checkpointer로 저장합니다. 처음에는 메모리(`MemorySaver`)라 서버를 다시 시작하면 사라졌고, 대화 키(`thread_id`)도 브라우저가 페이지를 열 때 만든 난수라 새로고침하면 새 대화가 되고 로그인 계정과 연결되지 않았습니다.

- **저장소**: LangGraph 공식 패키지 `langgraph-checkpoint-sqlite`(3.1.3)의 `SqliteSaver`. 새 DB 서버나 접속 정보 없이 파일 하나로 저장되고, 그래프 코드는 checkpointer만 바꾸면 됩니다. FastAPI가 요청을 여러 스레드에서 처리하므로 `check_same_thread=False`로 연결하고, 동시 접근은 `SqliteSaver` 내부 lock이 막습니다.
- **계정 연결**: `thread_id`는 브라우저가 보낸 값이 아니라 Spring이 로그인 계정으로 정합니다(`user:` + 아이디). 브라우저 값을 그대로 믿으면 다른 사람의 `thread_id`를 넣어 그 사람의 대화를 이어 쓰거나 볼 수 있기 때문입니다. 계정당 대화는 하나입니다.
- **화면 복원**: 채팅 화면을 열면 `/chat/history`(Spring) → `/history`(FastAPI)로 저장된 대화에서 사용자 질문과 최종 AI 답변만 골라 최근 50개를 다시 보여 줍니다(툴 호출·툴 결과는 제외).

```bash
cd ai-agent
python -m unittest test_chat_history -v

cd backend/loaagent
.\gradlew test --tests "com.esprit.loaagent.chat.ChatHistoryApiTest"
```

- Python(5건): 임시 SQLite 파일로 대화 후 연결을 닫고 새로 연결해도 대화가 남는지, 계정별로 따로 저장되는지, `/history`가 질문과 최종 답변만 최근 50개 돌려주는지 확인
- Spring(3건): 가짜 FastAPI로 브라우저가 다른 `thread_id`를 보내도 로그인 계정 값으로 바뀌는지, 기록 조회가 계정 값으로 가는지, 조회 실패 시 502와 빈 목록인지 확인
- 실제 서버 확인(2026-11-19, Gemini 3.1 Flash Lite): FastAPI에 "내 이름은 테스트야"를 보낸 뒤 서버를 껐다 켜고 `/history`로 두 메시지가 남아 있는 것과, "내 이름이 뭐라고 했지?"에 "테스트"라고 답하는 것을 확인

## RAG 검색 평가

```bash
cd ai-agent
python rag_eval.py
```

검색어마다 정답 청크(문서 + 섹션)를 정해 두고, 전체 청크를 유사도 순으로 정렬해 정답이 몇 등인지 측정합니다. Chroma와 로컬 Ollama(bge-m3)만 사용하고 Gemini는 호출하지 않습니다. 검색어 26개 = 일반 21개 + 헷갈리기 쉬운 검색어 5개(예: 세르카 1관문과 2관문에 모두 있는 "240줄").

| 지표 | 결과 |
| --- | --- |
| Hit@1 | 18/26 (69%) |
| Hit@2 | 23/26 (88%) |
| Hit@3 | 26/26 (100%) |
| MRR | 0.827 |
| **동적 k 적중** (서비스 규칙으로 정한 k개 안에 정답) | 수정 전 21/26 (81%) → **수정 후 24/26 (92%)** |

(2026-11-19 측정. 임베딩 검색은 같은 입력에 같은 결과를 내므로 1회 측정. Hit@k·MRR은 k 규칙과 무관한 검색 순위 지표라 수정 전·후가 같음)

**동적 k 규칙 수정**: 처음 측정에서 동적 k 안에 정답이 없었던 5건 중 4건은 k=1이 적용된 검색어였고, 정답은 2~3위에 있었습니다. k=1은 "줄", "카운터", "저스트 가드"처럼 좁은 패턴을 묻는 검색어에 적용됐는데, 이 단어들은 여러 섹션에 공통으로 나와 오히려 섹션을 구분하기 어려운 단어였습니다. 그래서 k=1 규칙을 없애고(기본 k=2, 전체·요약 질문 k=3), 같은 평가로 21/26 → 24/26을 확인했습니다. 남은 2건("세르카 난이도 종류", 레이드 이름 없는 "홀딩 저스트 가드")은 정답이 3위라 k=2로도 놓칩니다.

**실제 답변 확인 (Gemini 3.1 Flash Lite, 질문 5개, 1회)**: 서비스 그래프 전체(라우터 → Guide Agent → 검색 → 답변)를 수정 전·후 규칙으로 실행했습니다. 3.5 Flash Lite의 일일 한도를 넘어 3.1로 측정했고, 측정 스크립트 안에서만 모델을 바꿨습니다.
- 수정 전 규칙에서 "세르카 2관문 240줄 패턴 어떻게 해?"는 LLM이 "세르카 2관문 240줄 패턴"으로 정확히 검색했지만 k=1이라 1관문 청크만 받아 틀린 답을 했습니다. 위 평가에서 찾은 k=1 문제가 실제 답변에서도 재현됐습니다.
- Guide Agent 입력 토큰 합계는 5,709 → 5,993(약 5% 증가)이었습니다.
- 정답 섹션의 핵심 단어가 답변에 들어간 질문은 수정 전 3/5, 수정 후 2/5였지만, 이 차이는 k 규칙보다 **검색어 생성 문제** 때문이라 k 규칙의 효과로 해석할 수 없습니다. LLM이 검색어를 만들면서 사용자가 말한 레이드 이름을 다른 레이드 이름("카멘", "에기르", "에키드나" 등)으로 바꾼 경우가 검색 11회 중 6회였습니다.

**검색어 생성 규칙 추가**: 위 문제를 고치려고 Guide Agent 프롬프트에 "검색어에 사용자가 말한 레이드·보스 이름을 그대로 넣고, 다른 이름으로 바꾸거나 덧붙이지 말 것. 관문 번호와 줄 수도 유지할 것" 규칙을 넣었습니다. 프롬프트 예시에 테스트와 같은 이름이 들어가면 규칙이 아니라 예시 덕분에 맞힐 수 있어 예시 없이 작성했습니다.

| 공략 질문 8개 × 3회 (Gemini 3.1 Flash Lite) | 규칙 없음 | 규칙 있음 |
| --- | --- | --- |
| 검색어에 사용자가 말한 이름이 남아 있음 | 9/24 (회차별 3, 3, 3) | **17/24** (6, 4, 7) |
| 정답 섹션의 핵심 단어가 답변에 들어감 | 18/24 (6, 6, 6) | **23/24** (8, 7, 8) |

(2026-11-19 측정. 서비스 그래프 전체를 실행했고, 측정 스크립트 안에서만 모델을 3.1로 바꿨으며, 동적 k는 양쪽 모두 수정 후 규칙)
- "세르카 2관문 240줄", "벨가르딘 2관문 280줄"은 규칙이 없을 때 3회 모두 "카멘"으로 바뀌어 틀렸고, 규칙이 있을 때는 6회 중 5회 맞았습니다.
- **남은 문제**: 규칙이 있어도 "벨가르딘"을 "벨가르누스"처럼 비슷한 다른 이름으로 바꾼 경우가 남아 있고(24회 중 7회 이름 미유지), 이름은 유지하되 "카제로스 레이드 에키드나"처럼 다른 레이드 이름을 덧붙인 경우도 있었습니다(이 지표는 이름이 남아 있으면 유지로 셈). 청크가 6개뿐이라 검색어가 틀려도 정답 청크가 나오는 경우가 있어, 문서가 늘어나면 영향이 더 커질 수 있습니다.

- **한계**: 위 측정은 청크 6개 기준입니다. 평가 검색어는 직접 작성했고, 실제 답변 확인은 3.1 모델 기준이라 서비스 모델(3.5)에서의 결과는 확인하지 않았습니다. 핵심 단어 포함 여부는 답변 정확도를 대략적으로만 보여 줍니다.

### 공략 문서 확장 후 (청크 6개 → 19개)

공략 문서를 2개에서 6개로 늘렸습니다(칠흑 폭풍의 밤, 파멸의 성채, 최후의 날, 지평의 성당 추가). 새 문서는 나무위키 문서를 요약해 정리했고, 원문 전체를 읽지 못한 부분(파멸의 성채 2관문 후반, 최후의 날 2관문 후반·히든 페이즈)은 넣지 않았으며 출처와 빠진 범위를 각 파일 frontmatter의 `source`에 적었습니다.

| 측정 | 청크 6개 | 청크 19개 |
| --- | --- | --- |
| 기존 검색어 26개 - 동적 k 적중 | 24/26 | 22/26 |
| 기존 검색어 26개 - MRR | 0.827 | 0.771 |
| 전체 검색어 55개 - 동적 k 적중 | – | 47/55 (85%) |
| 전체 검색어 55개 - Hit@1 / Hit@3 / MRR | – | 76% / 89% / 0.835 |

추가한 검색어 29개 = 새 문서 21개 + 문서 간 혼동 6개(예: "진짜 찾기"는 세르카와 에키드나에 모두 있음) + LLM이 실제로 만든 잘못된 검색어 2개. 유형별 동적 k 적중은 일반 19/21, 혼동 3/5, 새 문서 19/21, 문서 간 혼동 5/6, 잘못된 검색어 1/2입니다. (2026-11-19 측정)
- **레이드 이름 없는 검색어가 크게 나빠짐**: "저저카저 연속 저스트 가드"(3위 → 8위), "홀딩 저스트 가드"(3위 → 11위)는 "저스트 가드"가 모든 문서에 나와 다른 레이드로 끌려갔습니다. 문서가 늘수록 검색어에 레이드 이름을 넣는 것(7-1 규칙)이 더 중요해집니다.
- **잘못된 검색어가 다른 문서로 감**: 벨가르딘을 물었는데 LLM이 만든 "카멘 2관문 280줄 카운터 타이밍"은, 청크 6개일 때와 달리 이제 실제 카멘 문서(칠흑 1관문)가 1위가 되어 정답이 5위로 밀렸습니다. 검색어 변형의 피해가 문서가 늘수록 커진다는 것을 확인했습니다.
- **섹션 제목에 없는 보스**: "아브렐슈드 난입 무력화"는 12위였습니다. 아브렐슈드는 '에키드나' 섹션 안에 한 줄로만 있어, 섹션 제목에 없는 보스는 찾기 어렵습니다. 섹션 제목에 함께 나오는 보스를 적거나 패턴 단위로 청크를 나누는 방법을 검토할 수 있습니다.
- 같은 문서 안의 비슷한 패턴("언령: 삭제"(1관문) vs "언령: 정지"(2관문))도 구분하지 못한 경우가 있었습니다.

### 문서에 없는 레이드·보스 거절

벡터 검색은 관련이 없어도 가장 가까운 문서를 돌려줍니다. 문서에 없는 "발탄 2관문 공략"은 벨가르딘 개요를, 존재하지 않는 "드래곤킹 바하무트 2관문 패턴"은 지평의 성당 개요를 1위로 돌려줬습니다. 거리 점수로 거르려 했지만, 문서가 있는 검색어(최대 0.915)와 없는 검색어(최소 0.918)의 차이가 너무 작아 기준을 정할 수 없었습니다.

그래서 `search_game_guide`가 검색 전에 **검색어에 문서 속 레이드·보스 이름이 있는지** 확인하게 했습니다.
- 이름 목록은 사람이 관리하지 않고, 서버 시작 시 적재된 문서의 `title`과 관문 제목에서 자동으로 뽑습니다(현재 41개). 문서를 바꾸면 서버를 다시 시작해야 반영됩니다.
- 오타는 비슷한 이름으로 통과시킵니다(`difflib` 유사도 0.6 이상, 예: "세르까" ↔ "세르카" 0.67).
- 이름이 없으면 검색하지 않고 "공략 문서가 있는 레이드 목록"과 함께 "문서 없음"을 돌려주며, 레이드 이름이 빠진 질문이면 어느 레이드인지 물어보도록 안내합니다.

| 측정 (`rag_eval.py`, 임베딩·Gemini 호출 없음) | 결과 |

| 문서 없는 검색어 거절 (실제 레이드 6개 + 존재하지 않는 보스 4개) | 10/10 |

- **잘못 거절된 9개**: 7개는 레이드 이름 없이 패턴만 쓴 검색어("홀딩 저스트 가드", "화염 메이든 빙고" 등), 1개는 섹션 제목에 없는 보스("아브렐슈드 난입 무력화"), 1개는 LLM이 바꾼 이름("벨가누스 거울 무력화 패턴")입니다. 이름 없는 검색어는 거리 점수로도 문서 없는 검색어와 구분되지 않았습니다(오히려 더 먼 경우가 많음).
- **실제 답변 확인 (Gemini 3.1 Flash Lite, 질문 4개, 1회)**: "발탄 2관문 패턴 알려줘", "에기르 1관문 기믹", "드래곤킹 바하무트 공략"은 모두 공략 문서가 없다고 답하며 문서가 있는 레이드 목록을 보여 줬고, "홀딩 저스트 가드 어떻게 해?"는 어느 레이드인지 되물었습니다. 다만 바하무트에는 "로스트아크에 존재하지 않는다"고 단정해, 문서가 없다는 것과 게임에 없다는 것을 구분하지 못했습니다.

## FastAPI 호출 타임아웃 테스트

가짜 FastAPI 서버(JDK 내장 `HttpServer`)로 정상 응답, 응답 지연, 서버 꺼짐, 500 응답을 만들어 상태 코드와 안내 문구를 확인합니다. Spring 컨텍스트를 띄우지 않아 MySQL 없이 실행됩니다.

```bash
cd backend/loaagent
.\gradlew test --tests "com.esprit.loaagent.chat.ChatApiControllerTimeoutTest"
```

## 회원가입 입력값 검증

회원가입 폼은 Bean Validation(`spring-boot-starter-validation`)으로 서버에서 검증하고, 오류가 있으면 저장하지 않고 입력값과 함께 필드별 오류 메시지를 보여 줍니다(비밀번호는 다시 채우지 않음).

| 항목 | 규칙 |
| --- | --- |
| 아이디 | 필수, 4~20자, 영문·숫자만 |
| 비밀번호 | 필수, 8~64자, 영문·숫자·특수문자만(공백·한글 불가) |
| 이메일 | 필수, 이메일 형식 |

비밀번호에 한글을 막는 이유: `BCryptPasswordEncoder`는 72바이트를 넘는 비밀번호에 예외를 던지는데(spring-security-crypto 7.1.2에서 직접 확인), 한글은 1자에 3바이트라 글자 수 제한만으로는 막을 수 없습니다. 1자 1바이트 문자만 허용하고 64자로 제한해 72바이트를 넘지 않게 했습니다.

```bash
cd backend/loaagent
.\gradlew test --tests "com.esprit.loaagent.member.MemberSignupValidationTest"
```

## 한계와 개선 계획

- 대화는 계정당 하나라 "새 대화"로 나눌 수 없고, 지우는 기능도 없음. 저장된 대화는 계속 쌓이지만 LLM에는 `trim_messages`로 최근 12,000토큰만 전달됨
- 대화 기록은 AI 서버 PC의 SQLite 파일에 있어 AI 서버를 여러 대로 늘리면 공유되지 않음(그때는 MySQL·Postgres 같은 DB checkpointer 필요)
- LLM 오류 안내는 FastAPI가 HTTP 200의 답변 문구로 돌려주므로, 채팅 화면에서는 오류 말풍선이 아닌 일반 답변 말풍선으로 보임
- 연결 끊김 같은 네트워크 오류가 `ModelConnectionError`로 변환되는지는 확인하지 못함(langchain-google-genai 4.4.2 소스에서는 HTTP 상태 코드 오류만 공통 예외로 변환). 변환되지 않으면 "그 외" 문구로 처리됨
- Spring 쪽 타임아웃은 기다림만 끊음 → FastAPI는 요청을 끝까지 처리하고 그 답변이 대화 기록(SQLite)에 남아, 사용자가 보지 못한 답변이 다음 질문의 맥락에 섞일 수 있음(새로고침하면 화면에는 보임)
- 응답 제한 시간 60초는 실측값이 아님. Gemini 클라이언트는 기본 `max_retries=6`, `timeout` 미설정(langchain-google-genai 4.4.2 기준)이라 API가 불안정하면 FastAPI 처리 시간이 60초를 넘을 수 있음
- 한 턴에 에이전트 하나만 실행 → 공략과 시세가 모두 필요한 질문(예: "세르카 가려면 재료값 얼마나 들어?")에는 반쪽 답만 가능. 에이전트 간 협업(handoff/planner) 검토 중
- Guide Agent가 검색어를 만들 때 레이드 이름을 바꾸는 문제는 프롬프트 규칙으로 줄였지만 남아 있음(Gemini 3.1 Flash Lite 측정에서 이름 유지 9/24 → 17/24). 프롬프트만으로는 완전히 막기 어려워, 사용자 질문의 레이드 이름을 코드로 검색어에 넣는 방식 등을 검토할 수 있음
- 문서에 없는 레이드는 거절하지만, "카멘 4관문"처럼 문서에 있는 이름을 다른 맥락으로 물으면 엉뚱한 문서(칠흑 1관문)를 근거로 답할 수 있음 → 관문 번호 확인, 모호하면 되묻기, LLM 검색 결과 판정 검토
- 벡터 검색만 사용 → 하이브리드 검색(BM25 + 벡터)과 리랭커 도입 검토 (리랭커는 순위·점수 기준 개선용, 조건 불일치 확인은 별도로 필요)
